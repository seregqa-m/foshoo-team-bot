# Общие календарные подписки и проверка названий

## Разовая генерация ссылок

Подписки общие: участнику достаточно готовой HTTPS/webcal-ссылки, вход в бот
или мини-приложение не нужен. Новых экранов в календаре нет.

По умолчанию читаем «Составы спектаклей»: для каждого имени собираем набор
спектаклей, затем оставляем уникальные наборы. Это только реальные комбинации
из таблицы, не все математически возможные подмножества. Одинаковый набор
у нескольких участников даёт одну ссылку. Имена участников не сохраняются
в подписке и не возвращаются в результатах/ICS; Telegram ID для неё не нужен.
Псевдонимы разрешаются через каталог. Неизвестные названия, неполные строки
и неоднозначные дубли имён требуют исправления до генерации.

24 ноября 2026 read-only проверка таблицы обнаружила 10 наборов:

- Любовь Громова
- Любовь Громова + Микрополь + Урод + Цианистый Калий
- Любовь Громова + Урод
- Любовь Громова + Урод + Цианистый Калий
- Любовь Громова + Цианистый Калий
- Микрополь
- Микрополь + Урод + Цианистый Калий
- Микрополь + Цианистый Калий
- Урод + Цианистый Калий
- Цианистый Калий

Это результат чтения на указанную дату; при пересборке составы читаются заново.

## Навык встроенного ассистента

Инструмент `rebuild_calendar_links` работает в двух режимах:

- «Пересобери общие ссылки на календарь по составам» — без аргумента
  `show_names`, все реальные комбинации из Google Sheets.
- «Сделай ссылку на Урод и Цианистый Калий» — `show_names` с явно указанными
  пользователем названиями; одна общая подписка на выбранный набор, даже если
  такой набор не встречается в составах. Sheets в этом режиме не читается.

Инструмент доступен администратору в существующем подтверждаемом контуре
ассистента. Подготовка только читает данные, проверяет названия и показывает
конкретные наборы. При подтверждении сервер перечитывает источник и сверяет
отпечаток; если наборы/каталог поменялись, публикация не выполняется до нового
подтверждения. Чужие action-токены и исполнение после потери прав отклоняются.
Повторное исполнение action-токена возвращает сохранённый результат.

После выполнения прямо в чате отображаются названия, webcal-кнопки и поле с
HTTPS-ссылками для копирования. Результат берётся из backend, не сочиняется LLM.
Существующие адреса для того же набора show ID сохраняются, новые наборы
добавляются. Ранее выданные ссылки остаются рабочими, даже если комбинация
исчезла из составов. Отозванные ссылки автоматически не включаются обратно.
В чаты бот сам ничего не рассылает.

Серверный CLI для первоначальной разовой генерации (окружение службы должно
быть загружено, Python только из её virtualenv):

```bash
cd /opt/foshoo/backend
/opt/foshoo/.venv/bin/python calendar_links_cli.py --preview
/opt/foshoo/.venv/bin/python calendar_links_cli.py --create --fingerprint <из-preview>
# Произвольный выбранный набор:
/opt/foshoo/.venv/bin/python calendar_links_cli.py --preview --show Урод --show 'Цианистый Калий'
/opt/foshoo/.venv/bin/python calendar_links_cli.py --create --fingerprint <из-preview> --show Урод --show 'Цианистый Калий'
# Отзыв по id из результата (не меняет остальные подписки):
/opt/foshoo/.venv/bin/python calendar_links_cli.py --revoke <id>
```

## Подключение и обновления

- Apple Calendar и другие клиенты с webcal: открыть webcal-ссылку.
- Google Calendar: на компьютере «Другие календари» → «Добавить по URL»,
  вставить HTTPS-ссылку. [Инструкция Google](https://support.google.com/calendar/answer/37100).
- Нужна подписка по URL, а не разовый импорт файла `.ics`.

Каждая ссылка сохраняет выбранный набор show ID. Новые репетиции и показы,
переносы и отмены этих спектаклей попадают в подписку при синхронизации.
Пользователи одной ссылки получают одно расписание. Изменения составов
не меняют её содержимое: для нового набора используется другая ссылка.

Окно выдачи — последние 30 и следующие 90 дней. Повторы выдаются отдельными
экземплярами со стабильными UID, отмены — `STATUS:CANCELLED`, время — UTC,
события на весь день — `VALUE=DATE` с исключающей конечной датой.
Формат: [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545).
Скорость обновления зависит от стороннего клиента; мгновенность не гарантируется.

ICS читает только локальный календарь и каталог: Sheets, Telegram, финансовый
доступ и активность создателя ссылки ему не нужны. Публичная выдача защищена
случайным отзываемым токеном (256 бит), не Telegram initData. Экспортируются
названия, время и место; описания, составы и ответы на опросы не экспортируются.
Остальные API по-прежнему требуют подписанную Telegram-идентичность.

Ссылка доступна любому её обладателю. Отзыв прекращает дальнейшее чтение,
но не удаляет уже скачанные копии у подписчиков. Ссылки не коммитятся и
не публикуются в общей документации; HTTP access logs могут содержать токены.

## Watcher названий

Проверка идёт после успешной фоновой синхронизации календаря с периодом
`SYNC_INTERVAL_MINUTES` (по умолчанию 15 минут), независимо от автоматизации
опросов. В `RECOVERY_MODE` она не запускается. Если синхронизация не удалась,
проверка переносится до следующего успешного прохода.

Первый проход сохраняет исходное состояние без уведомлений о старых ошибках.
Далее проверяются новые будущие события и изменения названий:

- пустое название;
- конфликтующие типы репетиции и показа;
- репетиция без однозначного названия/псевдонима спектакля из каталога.

Допустимы «Название [Реп]», «Репетиция [Название]», «Название [Спект]»,
«Спектакль [Название]» и остальные уже поддерживаемые формы типа.
Известное название без метки (например, «УРОД») означает показ и не является
ошибкой. Watcher сохраняет это же правило, что и основной календарь.
Внешний показ с явным типом может не иметь записи в каталоге. Отсутствие чата
не является ошибкой названия. Аренда, уборка и другие обычные события не
помечаются. Полностью неизвестное название без распознаваемого типа нельзя
надёжно отличить от обычного события — watcher не пытается угадывать.
Ручное назначение спектакля для опроса не исправляет некорректное название.

Получатели — текущие записи `superadmins`, включая первоначального владельца,
если его роль не отозвана. Каждый должен ранее начать личный диалог с ботом
и не блокировать его. Сообщение содержит название, дату, объяснение и ссылку
на событие Google Calendar. Ничего автоматически не переименовывается.

Для повторов одной серии с одинаковой ошибкой приходит одно предупреждение.
Успешные отправки сохраняются отдельно для каждого суперадминистратора и не
повторяются после перезапуска. При неудачной отправке повтор не раньше часа;
сбой у одного получателя не блокирует остальных. За проход — не более 20
попыток отправки. Telegram не предоставляет идемпотентный sendMessage:
при потере ответа после фактической доставки редкий дубль всё же возможен.
Исправленные/отменённые/прошедшие события больше не отправляются.

## Развёртывание

Новых зависимостей и env-переменных нет. `MINI_APP_URL` должен указывать на
публичный HTTPS-сайт приложения: его origin используется для ссылок.
Существующий Nginx `location /api/` обслуживает новый ICS endpoint.

Старт создаёт `calendar_shared_subscriptions`, `calendar_watch_state`,
`calendar_watch_deliveries`; миграция добавляет `is_all_day`, `google_html_link`,
`recurring_event_id` в `calendar_events`. Первая синхронизация заполняет
метаданные старых событий. Данные не удаляются. Развёртывание — один worker.
Новые события из планировщика создаются с явным `[Спект]`.

Assistant capability audit: новый подтверждаемый инструмент
`rebuild_calendar_links`, серверная подготовка конкретных наборов, защита от
смены источника между preview и execute, показ структурированного результата
в существующем чате. Watcher не использует LLM.
