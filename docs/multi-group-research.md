# Один FoShoo-бот для нескольких групп

Исследование по текущему коду и документации Telegram, 17 сентября 2026. Это проект решения, поддержка нескольких групп пока не реализована.

## Вывод

Один @foshoo_bot и один backend могут обслуживать несколько групп. Отдельный сервер или новый бот на каждую труппу не обязательны. Главная работа — разделение данных, полномочий и фоновых задач по группе. Простого добавления нескольких chat_id недостаточно.

## Возможности Telegram

- Отправка сообщений и опросов адресуется через chat_id. Получение ответов на свои неанонимные опросы доступно через poll_answer; связь poll_id с группой надо хранить у себя. [Bot API](https://core.telegram.org/bots/api#pollanswer).
- Для надёжной проверки участника через getChatMember бот должен быть администратором соответствующего чата. Изменения статуса самого бота приходят через my_chat_member; переход группы в супергруппу меняет chat_id. [Проверка участника](https://core.telegram.org/bots/api#getchatmember), [обновления](https://core.telegram.org/bots/api#update), [Message](https://core.telegram.org/bots/api#message).
- Прямая ссылка Mini App поддерживает startapp, chat_type и chat_instance. chat_instance нельзя считать числовым Bot API chat_id. Ссылкой можно передать идентификатор зарегистрированной группы, но сервер всё равно обязан проверить подписанный initData и членство/права в этой группе. [Mini Apps](https://core.telegram.org/bots/webapps#direct-link-mini-apps).
- Telegram ограничивает частоту отправки: ориентиры — 1 сообщение/секунду в чат, 20/минуту в группу, около 30/секунду для массовой рассылки. Нужны очередь и обработка retry_after, а не отдельный сервер для каждой группы. [Bots FAQ](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this).

## Что сейчас мешает в нашем коде

| Участок | Сейчас | Что потребуется |
|---|---|---|
| core/access.py | Один GROUP_CHAT_ID; ADMIN_ID даёт глобальные права; кэш по пользователю | Проверка членства/админства конкретной группы; ключ кэша (group_id, user_id); отделить владельца платформы от админа труппы |
| notifications/router.py, main.py | Настройки и расписание автоопросов берутся из строки ADMIN_ID | GroupSettings: фильтр событий, спектакль, часовой пояс, дни/время и флаги напоминаний |
| availability/router.py | Создание кампании удаляет все предыдущие кампании; общий список текущих опросов | Кампании/опросы/выборы с group_id; замена только внутри группы; лучше история по месяцу |
| polling и bot.py | Отправка, закрепление, ссылки и ответы привязаны к одному чату | Хранить chat_id вместе с message_id и poll_id; находить группу через сохранённый опрос |
| calendar и Google sync | Один Google Calendar и фильтрация по названию | Явная связь события с группой; уникальность внешнего события по (calendar_id, google_event_id) |
| sheets_client.py | Одна таблица, фиксированные названия листов; имена/username как связь с актёром | Источник данных на группу; постоянный Telegram user_id и участие человека в нескольких группах |
| frontend | Нет выбранной группы; экраны и сохранённые черновики общие | Переключатель группы; сброс/разделение кэшей, форм, ошибок и незавершённых действий |
| assistant | Общие контекст, память диалога и действия | group_id в контексте, ключе сессии и токене подтверждения; проверка группы при выполнении каждого инструмента |
| finance, links, afisha | Общие финансы, ресурсы, файлы | Явно решить, что общее театру, а что доступно только группе; до решения закрыть новым группам |

## Предлагаемая модель

- Group: внутренний id, уникальный telegram_chat_id, название, статус подключения, настройки источников.
- GroupMember: (group_id, telegram_user_id), роль и состояние членства. Один человек может состоять в нескольких группах.
- GroupSettings: параметры автоопросов, спектакли/фильтры, часовой пояс.
- group_id у кампаний занятости, опросов, назначений спектаклей и действий ассистента; у событий — явная принадлежность или таблица связей, если они общие.
- Ответ на опрос хранить в БД по актёру и дате с источником (campaign/poll). Сейчас AvailabilityVote хранит только факт ответа, а варианты остаются в Sheets: этого недостаточно для надёжной самостоятельной многогрупповой системы.
- Одновременные планы одного актёра в разных группах проверять отдельно. Решить продуктовую политику: занятость общая или ответы независимы по каждой труппе. Не раскрывать другой группе приватные детали события без договорённости.

## Как будет выглядеть подключение

1. Администратор добавляет существующего бота в чат и выдаёт права, нужные для опросов/закреплений и проверки членства.
2. Командой подключения в этом чате регистрирует группу; backend проверяет его права именно там. Само приглашение бота не открывает доступ к данным театра.
3. Указывает название группы и её источник расписания/составов. На пилоте проще отдельные таблицы и календари для каждой группы.
4. Получает ссылку на приложение с выбранной группой. В личном чате приложение предлагает только доступные этому человеку группы.
5. Настраивает автоопросы, спектакли и время. Предпросмотр показывает название и чат получателя перед первой отправкой.

Это предложенный UX, таких команд и экранов в текущей версии нет.

## Порядок внедрения

1. Добавить модель групп, создать из нынешней конфигурации первую группу и мигрировать её данные. Старые опросы продолжают принимать ответы.
2. Закрыть доступы по group_id на сервере: все чтения, изменения, подтверждения ассистента и кэши. Покрыть тестами запрет доступа к чужим id.
3. Перевести фоновые задачи на обход активных групп с независимыми сбоями, блокировками от дублей и ограничением отправки. Оставить один потребитель Telegram updates для одного токена.
4. Добавить регистрацию чата, переключатель и источники; пилот на второй группе с отдельными данными.
5. Затем решать общие финансы, общих актёров и единый театр. Не смешивать этот этап с первым подключением.

## Проверки перед второй группой

- Админ группы A не может читать/менять настройки и данные группы B подстановкой id или ссылки.
- Ответы на старые и новые опросы записываются в правильную группу; отмена ответа также.
- Новая кампания A не удаляет кампанию B; удаление бота из A выключает только задачи A.
- Смена группы не переносит формы расходов, выбранные даты и подтверждения ассистента.
- Сбой Google или Telegram в A не останавливает задачи B; повтор запроса не создаёт второй опрос.
- Корректно обработаны смена username, выход участника и миграция chat_id.

## Объём и инфраструктура

Это изменение архитектуры приложения, а не косметическая настройка. Для нескольких небольших групп я бы сохранила FastAPI + React и один сервер, а ёмкость проверила по фактической нагрузке. Отдельные экземпляры с отдельными токенами проще изолировать для срочного пилота, но потребуют дублировать настройки и обновления. Для постоянного использования рекомендую один бот с разделением данных по группам.

До разработки нужно согласовать: общие ли финансы, одна ли таблица/календарь, бывают ли актёры в нескольких группах, кто подключает новые группы и имеет доступ ко всему театру. Проверка выполнена по коду и документации; подключение второго живого чата и нагрузочный тест не проводились.
