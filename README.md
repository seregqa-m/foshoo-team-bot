# Foshoo Theatre Bot

Telegram Mini App для управления театральной студией: расписание (Google Calendar), опросы посещаемости, финансы и настройки. Главная вкладка — расписание; AI-ассистент подключается через Cloud.ru, комментарии проверяются локальными регулярками.

**Перенос в Selectel:** [инструкция и команды](docs/selectel-quickstart.md), шаблоны nginx/systemd/env в `deploy/`. Переделка архитектуры остаётся на паузе.

## Стек

- **Backend**: FastAPI + aiogram (запускаются в одном процессе)
- **Frontend**: React (Telegram Mini App)
- **БД**: SQLite
- **AI**: выключен; код интеграции Yandex сохранён для возможного возвращения
- **Интеграции**: Google Calendar API, Google Sheets API

## Переменные окружения (`.env`)

```env
# Telegram
BOT_TOKEN=                  # токен от @BotFather
TELEGRAM_PROXY_URL=         # необязательно: socks5://login:password@host:port
ADMIN_ID=                   # ваш Telegram ID (@userinfobot)
MINI_APP_URL=               # HTTPS URL фронтенда (например https://app.example.com)
GROUP_CHAT_ID=              # прежняя группа: проверка доступа и адрес старых опросов

# Google
GOOGLE_CALENDAR_JSON=backend/credentials.json
GOOGLE_CALENDAR_ID=         # ID календаря Google
GOOGLE_SHEETS_ID=           # ID Google Sheets (маппинг актёров, расписание, финансы)

# Прочее
SYNC_INTERVAL_MINUTES=60
SECRET_KEY=                 # секрет для подписи JWT action_token ассистента

# AI-ассистент (Cloud.ru Foundation Models)
LLM_PROVIDER=cloudru
CLOUDRU_API_KEY=            # Key Secret API-ключа для сервиса Foundation Models
CLOUDRU_MODEL=openai/gpt-oss-120b
LLM_MAX_TOKENS=4096
LLM_ENABLED=false
ASSISTANT_ENABLED=false
RECOVERY_MODE=false
POLL_AUTOMATION_ENABLED=true
```

## AI-ассистент

В шаблонах нового развёртывания ассистент выключен. В рабочем Cloud.ru включён 21 октября 2026: `LLM_PROVIDER=cloudru`, модель `openai/gpt-oss-120b`, оба флага `LLM_ENABLED=true` и `ASSISTANT_ENABLED=true`. Ключи Yandex для этого провайдера не требуются. Возможности:

- Отвечать на вопросы про данные приложения (баланс, ближайшие события, недавние траты, состав спектакля, активные опросы, кампания занятости) — свежий snapshot автоматически инжектится в промпт, обращения к Sheets кешируются на 60 сек.
- Углубляться через read-tools: `search_expenses`, `get_events_in_range`, `get_show_cast`.
- Выполнять действия через write-tools с обязательным подтверждением: добавить расход/доход, создать/обновить событие, запустить/остановить опрос посещаемости, создать кампанию занятости, пингануть неответивших, изменить глобальные настройки, загрузить новую афишу на сайт.
- Каждое write-действие проходит через preview-карточку с кнопкой «Выполнить». Токен действия — JWT со сроком жизни 5 мин, подпись `SECRET_KEY`.
- Удаления в реестре tools нет — деструктивные просьбы отклоняются, направляются в UI.
- Аномалии сумм ассистент замечает сам, опираясь на 30-дневную статистику расходов в инжектированном контексте (не хардкод в env).
- Настройки автоопросов и таблица «Спектакль — ID чата» доступны администратору в отдельной вкладке «Настройки», независимо от ассистента.

Действия ассистента логируются в таблицу `assistant_action_log` (`user_id`, `tool_name`, args, результат, ошибка, токены).

### Настройка Cloud.ru

1. Создать сервисный аккаунт уровня «Проект». В основной [инструкции аутентификации](https://cloud.ru/docs/foundation-models/ug/topics/api-ref__authentication) назначение ролей опционально.
2. Создать API-ключ с сервисом **Foundation Models** и сохранить Key Secret в серверной переменной `CLOUDRU_API_KEY`.
3. Установить `LLM_PROVIDER=cloudru`, `CLOUDRU_MODEL=openai/gpt-oss-120b`, `LLM_MAX_TOKENS=4096`. Ключ хранится только на backend, не во frontend.
4. Проверить на искусственных данных ответ модели и цикл вызова инструмента. Лимит токенов учитывает reasoning; ответ, содержащий только reasoning без публичного текста или инструмента, отклоняется.
5. После проверки выставить `LLM_ENABLED=true` и `ASSISTANT_ENABLED=true`, перезапустить backend. Существующая вкладка появится у пользователей с доступом к ассистенту; первоначальным экраном остаётся расписание. В recovery-режиме API агента недоступен.

Клиент использует `https://foundation-models.api.cloud.ru/v1/chat/completions`, Bearer-аутентификацию и `parallel_tool_calls=false`. Подтверждения действий, права доступа и защита от повторного выполнения сохраняются. Автоматического перехода к другому провайдеру нет. Модерация комментариев остаётся на локальных правилах.

### Настройка YandexGPT (прежний провайдер)

Для прежнего провайдера явно задать `LLM_PROVIDER=yandex`. Если переменная отсутствует, используется Yandex для совместимости с существующей конфигурацией.

1. [console.cloud.yandex.ru](https://console.cloud.yandex.ru) → каталог, где будет жить SA
2. В каталоге активировать сервис Yandex Foundation Models
3. IAM → сервисный аккаунт → добавить роль `ai.languageModels.user`
4. Создать API-ключ этого SA. Зона видимости (scope) — `yc.ai.languageModels.execute` (узкая) или `yc.ai.foundationModels.execute` (широкая, если позже добавите SpeechKit)
5. Прописать `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` в `.env`, перезапустить бэкенд

## Запуск на сервере (production)

Для **нового сервера Selectel** использовать [отдельную инструкцию](docs/selectel-quickstart.md): сборка на Mac, один worker, `/etc/foshoo.env`, режим восстановления. Ниже описан прежний способ обновления уже настроенного Git checkout; к архивной установке он автоматически не применяется.

Для действующего Linux-сервера с systemd есть команда `./bot`. Один раз из корня
проекта, под обычным пользователем (`seregqa`, без `sudo` перед всей командой):

```bash
git pull --ff-only
./bot setup --build
```

Она установит службу `foshoo-bot`, соберёт фронт, завершит прежний запуск
`python3 backend/main.py` из этого проекта и запустит backend через systemd.
При необходимости сама запросит пароль sudo. Служба работает от твоего пользователя,
с Python из `venv/bin/python3` (или `backend/venv/bin/python3`) и рабочей директорией
в корне проекта. Backend сам читает `.env`; активировать venv вручную не нужно.
Фронт публикуется в `frontend/build`, как и при обычном `npm run build`.

Дальше достаточно одной команды:

```bash
./bot restart          # перезапустить только backend
./bot restart --build  # собрать фронт и перезапустить backend
./bot status           # состояние службы
./bot logs             # последние 100 строк и новые логи; Ctrl+C — выйти
```

Из любой папки можно вызвать `~/foshoo-team-bot/bot restart --build`.
Для обновления кода из GitHub и полного перезапуска:

```bash
git pull --ff-only && ./bot restart --build
```

`--build` выполняет `npm ci` и сборку во временную папку. Ошибка установки или
сборки оставляет прежний фронт и backend работающими. После успешной сборки
заменяется `frontend/build`; nginx перезапускать не требуется, если он уже
обслуживает эту папку. При отдельном каталоге публикации nginx нужно сохранить
свой шаг копирования или изменить его root на `frontend/build`.

Сохрани прежний `REACT_APP_API_URL` в `frontend/.env.production` либо передавай его
при сборке, например `REACT_APP_API_URL=https://ваш-домен.com ./bot restart --build`.
Backend использует настройки из `.env`, а не переменные интерактивного shell.
При изменении Python-зависимостей сначала выполни
`venv/bin/python3 -m pip install -r backend/requirements.txt`.

Служба автоматически запускается после перезагрузки сервера и перезапускается
при аварийном завершении (с ограничением частых сбоев). Команда перезапуска ждёт
успешного `/health`. Это проверка готовности HTTP API; связь с Telegram и Google
проверяется отдельно. После перехода `nohup`/`pkill` больше не нужны, новые логи
идут в журнал systemd, а прежний `~/bot.log` остаётся на месте.

Настройка рассчитана на Linux с systemd, Python 3.9+ и Linux 5.3+ для автоматической
остановки прежнего процесса. Если старый backend запущен из другой папки, setup
остановится до переключения: сначала нужно сверить путь к SQLite. Конфигурация
другой службы с именем `foshoo-bot` не перезаписывается. На локальном macOS
команды управления службой недоступны. За службу отвечают стандартные
[параметры systemd](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml);
отдельный путь сборки поддерживается
[Create React App](https://create-react-app.dev/docs/advanced-configuration/).

Для ручного запуска при разработке:

```bash
# Из корня проекта
venv/bin/python3 backend/main.py

# В другом терминале, тоже из корня проекта
npm --prefix frontend start
```

### Подключение Telegram через прокси

Если сервер не может подключиться к Telegram напрямую, добавьте в серверный `.env`:

```dotenv
TELEGRAM_PROXY_URL=socks5://LOGIN:PASSWORD@HOST:PORT
```

Для HTTP CONNECT используйте `http://LOGIN:PASSWORD@HOST:PORT` (даже если
провайдер называет услугу HTTPS-прокси). Спецсимволы в логине и пароле нужно
percent-encode, например `@` → `%40`, `#` → `%23`. MTProto не поддерживается.
Без переменной или с пустым значением бот подключается напрямую.

После `git pull` установите зависимости в виртуальное окружение приложения
командой `python -m pip install -r backend/requirements.txt` из корня проекта
и перезапустите backend своим менеджером процессов. Для Docker Compose:
`docker compose up -d --build backend` — переменная передаётся в контейнер.

Прокси используется общей сессией бота: для получения голосов, отправки опросов,
сообщений и закреплений. Google-интеграции работают как раньше.
Проверьте на сервере появление в логах `Bot polling active`, затем создание
тестового опроса и сохранение голоса в приложении. Один лог запуска сам по себе
не подтверждает доступность Telegram. `.env` с паролем прокси не коммитьте.

### Пример nginx конфига

```nginx
server {
    server_name ваш-домен.com;

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        root /путь/к/frontend/build;
        try_files $uri $uri/ /index.html;
    }

    listen 443 ssl;
    # ssl_certificate ...
}
```

## Обновление афиши

Вкладка «Ресурсы» содержит блок «Афиша на сайте». Также можно попросить ассистента: «загрузи новую афишу».

Механика: при загрузке нового файла текущая афиша (`afisha-new`) автоматически становится архивной (`afisha-old`), а загруженный файл занимает место `afisha-new`. ID файлов на Google Drive не меняются — ссылки на сайте продолжают работать.

Настройка (один раз):
1. В Google Cloud Console включить **Google Drive API** (тот же проект, что Calendar и Sheets)
2. Найти email сервисного аккаунта в `backend/credentials.json` (поле `client_email`)
3. Открыть оба файла афиши на Google Drive → «Настроить доступ» → добавить email SA с ролью **Редактор**
4. Скопировать ID файлов из URL (`drive.google.com/file/d/**{ID}**/view`) и прописать в `.env`:
   ```
   AFISHA_NEW_DRIVE_FILE_ID=...
   AFISHA_OLD_DRIVE_FILE_ID=...
   ```
5. В nginx конфиге добавить `client_max_body_size 20m;` в блок `location /api/`

## Google Calendar и Sheets

1. Google Cloud Console → создать проект → включить **Google Calendar API** и **Google Sheets API**
2. IAM → Сервисные аккаунты → создать → скачать JSON-ключ
3. Положить файл в `backend/credentials.json`
4. В настройках Google Calendar → поделиться с email сервисного аккаунта (роль: редактор)
5. Google Sheets → поделиться с тем же email сервисного аккаунта
6. Прописать `GOOGLE_CALENDAR_ID` и `GOOGLE_SHEETS_ID` в `.env`

Ожидаемая структура Sheets:
- Вкладка **Труппа** — столбец A: имя, столбец J: telegram username
- Вкладка **Составы спектаклей** — столбец A: название спектакля, B: роль, C: актёр
- Вкладка **График [составы]** — строка 1: заголовки дат, столбец A: имя актёра
- Вкладка **Финансы** — ячейка G4: сумма копилки; именованные таблицы расходов/доходов

В приложении финансовая сводка переключается между «Копилка», «Статистика»
и «К возврату». Копилка по-прежнему берётся из G4, графики сохраняют свои
периоды и фильтры. «К возврату» показывает по каждому человеку сумму личных
трат минус операции типа «Возврат» по всем проектам в двух колонках: за всё время
и за последние 30 дней (сегодня и 29 предыдущих дней по часовому поясу приложения).
Вторая колонка учитывает только траты и возвраты внутри периода, а не распределяет
возвраты по конкретным покупкам; отрицательный итог человека показывается как ноль.
Пожертвования и траты со счёта ФоШу не входят в эти суммы. Люди без положительного
остатка в обоих периодах не показываются; переплата одному не уменьшает долг
перед другим. По нажатию на имя открывается полная история личных трат и
возвратов, перемешанных по дате от новых к старым; операции без даты идут в конце.
Имена сопоставляются без учёта регистра и лишних пробелов, без угадывания
псевдонимов. Операции без имени отмечаются отдельно; возврат без получателя
не вычитается из чьего-либо долга, а итог помечается как предварительный.

В поле «Кто потратил» для типа «Трата со счета ФоШу» автоматически стоит
«Копилка»; это значение сохраняется и в Google Sheets. Старые операции
показываются так же, но их исходные строки не переписываются. Для личных
трат нужен человек, для возврата — получатель («Кому вернули»).

## Локальная разработка

```bash
# Backend
cd backend
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
python main.py

# Frontend
cd frontend
npm install
REACT_APP_API_URL=http://127.0.0.1:8000 npm start
```

Для тестирования Mini App локально нужен HTTPS-туннель:
```bash
cloudflared tunnel --url localhost:3000
# Скопируйте URL в MINI_APP_URL в .env и перезапустите backend
```

## Доступ и подтверждения действий

Все `/api/*` запросы требуют заголовок `X-Telegram-Init-Data` с исходным
`Telegram.WebApp.initData`. Сервер проверяет HMAC-подпись и возраст данных
(до 24 часов); `initDataUnsafe`, `user_id` и `username` сами по себе доступ не дают.
После истечения срока нужно закрыть и заново открыть Mini App.

Участники подключённых групп могут входить по текущему членству, в том числе
без username и без записи в Google Sheets. Членство проверяется на каждом
запросе: выход из всех подключённых групп или снятие их привязок отзывает
этот способ доступа. Автоматически созданная строка в «Труппе» не даёт
бессрочный доступ и не открывает финансы.

Прежний отдельный доступ участников из листа «Труппа» сохраняется, включая
добавление расходов и доходов. Его источник фиксируется перед первой
автоматической записью в Sheets. Управлять календарём, опросами, общими настройками, афишей и удалять
финансовые записи могут суперадминистраторы и администраторы `GROUP_CHAT_ID`.
Обычные права кешируются на 60 секунд; глобальная роль проверяется в БД на каждом
запросе. Если проверить состав нельзя, обычному участнику доступ не предоставляется;
суперадминистратор не зависит от Google Sheets.
В обычном браузере без запуска через Telegram доступ к данным закрыт.

Первый суперадминистратор однократно переносится из `ADMIN_ID` при запуске.
Дальше глобальные роли выдаются и снимаются в настройках приложения, в разделе
«Управление театром → Суперадминистраторы». Снятая роль не возвращается после
рестарта; последнего суперадминистратора удалить нельзя. `ADMIN_ID` пока сохраняйте
прежним: он ещё используется как ключ настроек действующей группы.
История внедрения нескольких групп: [план и проверки](docs/multi-group-rollout.md).

В настройках суперадминистратора добавлен раздел **«Спектакли и чаты»**:
таблица **«Спектакль — ID чата»**. Введите ID в строке спектакля и нажмите
«Сохранить»; пустой ID снимает привязку. Точный ID можно получить командой `/chatid` в нужной группе:
бот ответит числом, которое нужно скопировать целиком, включая минус.
ID из адресной строки Telegram Web может отличаться от ID Bot API.
При проверке различаются неверный/устаревший ID, отказ доступа, сетевой сбой,
ограничение частоты запросов и ошибка разбора ответа Telegram; права не меняются автоматически.
Чат проверяется и регистрируется при сохранении строки, отдельной регистрации в интерфейсе нет. Проверка требует
админства бота и права закреплять сообщения; сообщений в чат она не отправляет. Повторный
импорт сохраняет маршруты, включая спектакли, переименованные в приложении.
Изменения доступны только суперадмину и записываются в журнал.

Блоки «Текущий репетируемый спектакль» и «Основная группа» удалены из настроек.
Групповой фильтр названий больше не используется. Маршруты работают по спектаклю:
опрос репетиции, автоопрос и напоминание идут в чат спектакля из этой таблицы.
Для автоопросов укажите в названии события тип и спектакль, например
`Репетиция [Урод]` или `Урод [Реп]`. Если спектакль не определён однозначно, кнопка **«Опрос»** в
карточке репетиции предлагает список существующих спектаклей. Выберите спектакль
и нажмите **«Отправить опрос»**. Спектакли без настроенного чата видны в списке,
но недоступны для отправки. Выбор сохраняется для этой репетиции и её напоминаний;
название в Google Calendar не меняется. При переименовании события спектакль
определяется заново. Автоопрос ждёт, пока спектакль будет определён;
запасной рассылки в общую группу нет.

В опросе занятости выбранные спектакли определяют чаты публикации. Если
несколько спектаклей связаны с одним чатом, копия будет одна. Голоса из обоих
типов опросов объединяются по **человеку и дате** во вкладке «Планирование составов».
Последнее изменение ответа за дату действует для всех спектаклей. Изменение
другой даты в длинном опросе не перезаписывает этот ответ. Смена спектакля
сохраняет доступность; перенос на другой день требует ответов за новый день.
Человек, ответивший в другом опросе на ту же дату, не получает повторный тег.

Ответы хранятся в базе бота и экспортируются в «График [составы]». Ошибки
Sheets повторяются фоновым процессом, принятые голоса сохраняются. Назначенные
роли не затираются; новый отказ после назначения виден в планировании.
Составы и роли пока редактируются в Sheets. После появления ответа в базе
ручная правка «да/нет» в Sheets не заменяет его — изменить доступность нужно
голосованием. В планировании показываются все спектакли из настроек и прежние
спектакли Sheets; без списка ролей спектакль отмечается как неполный.

Новые участники регистрируются по голосам в неанонимных опросах бота:
обычных и месячных. Открывать приложение не требуется. После проверки
членства в подключённой группе бот добавляет недостающие строки в «Труппу»
и «График [составы]», затем выгружает ответ. Проверка и повторные попытки
выполняются раз в минуту независимо от `POLL_AUTOMATION_ENABLED`; режим
восстановления останавливает всю внешнюю работу.

В «Труппе» имя остаётся в A, username — в J, а колонка `Telegram ID`
находится по заголовку или добавляется после занятых колонок. Запись
связывается по ID либо единственному прежнему username без другого ID.
Совпадение имён не объединяет людей: для однофамильцев добавляется суффикс
`[TG ID]`. Человек без username тоже регистрируется и выгружает ответы.
Прежнее имя актёра сохраняется; для нового используется имя из Telegram.
При неоднозначных привязках запись откладывается до исправления таблицы,
но сам голос сохраняется. Одновременное ручное добавление/перестановку строк
в Sheets лучше выполнять при остановленной синхронизации.

Регистрация не назначает роли и не добавляет человека в лист составов спектаклей.
В базе хранится отдельное членство человека в каждом чате. События `chat_member`
обновляют вступления и выходы; каждые пять минут проверяются уже известные люди,
что восстанавливает пропущенные события. Бот должен оставаться администратором.
Полный состав чата Telegram не предоставляет: список растёт по голосам и событиям
вступления. При обновлении известные ID из сохранённых голосов ставятся на проверку,
исторические ответы не придумываются.

Напоминания используют зарегистрированных участников конкретного чата и общие
ответы за дату. Перед отправкой членство перепроверяется; при сбое проверки
рассылка откладывается. Упоминания по Telegram ID работают без username.
В «Спектакли и чаты → Участники подключённых групп» доступен просмотр списка.
В занятости учитываются все зарегистрированные действующие участники чата;
напоминания получают те, кто ещё не ответил за соответствующую дату.

В планировании показаны количество зарегистрированных участников, «смогут»,
«не смогут», «не определились» и «не ответили», даже без списка ролей.
Назначение спектакля по-прежнему требует заполненных ролей и полного состава.

Обновлять нужно backend и frontend. Миграции выполняются при запуске,
сохраняя существующие опросы и ответы. Старые публикации получают исходный
чат из `GROUP_CHAT_ID`; новую маршрутизацию задаёт только таблица настроек.
Повторная отправка кампании с теми же датами и адресатами не создаёт копии.
После неопределённого сетевого сбоя сначала проверьте указанный чат; интерфейс
попросит подтвердить отсутствие публикации перед повтором.
Добавление чата даёт его участникам обычный доступ, но не финансовые или административные права.
[Проверка после обновления](docs/multi-group-rollout.md).

Подтверждения ассистента учитываются в `assistant_executions` по `jti` токена.
Повтор подтверждения возвращает сохранённый результат. Если процесс оборвался
после начала операции или внешний сервис не подтвердил результат, тот же токен
не запускает операцию повторно: сначала нужно сверить таблицу/календарь/Telegram.
Это защита от повторного запуска, а не распределённая транзакция с Google.
Новая таблица создаётся автоматически; существующая БД должна сохраняться между
перезапусками. Если `SECRET_KEY` не задан, ключ подписи выводится из `BOT_TOKEN`.

## Синхронизация и время

Календарь загружает все страницы Google. Отсутствующие события отменяются
только внутри окна успешно завершённой полной загрузки; связанные опросы
деактивируются. В SQLite время событий хранится как местное время `TIMEZONE`
(по умолчанию Europe/Moscow) для совместимости со старой БД. При записи значения
с часовым поясом приводятся к нему, в API даты возвращаются с явным смещением.
Аудит и срок действия опросов остаются в UTC.

Google Calendar синхронизируется за 365 дней назад и 90 дней вперёд.
Более старая история, уже сохранённая в БД, не удаляется по возрасту.
Расписание запрашивает сохранённую историю и ближайшие 60 дней: завершённые
события остаются в календарной сетке и бледнеют, но скрываются из списка.
В списке отображаются только текущие и будущие события.
Признак завершения определяется по времени окончания и обновляется каждые
30 секунд, пока вкладка активна.

Редактирование доступно администраторам: карандаш в карточке или нажатие на
событие в сетке открывает свежие данные из Google Calendar. Для повторяющихся
событий есть выбор «Только это событие» / «Вся серия». Второй вариант читает
и изменяет родительское событие Google, включая прошлые повторы; даты в форме
относятся к первому событию серии. Новая серия не создаётся, правило повторения
не меняется. При переключении области черновики формы сохраняются отдельно.
Сохранение сразу отправляется в Google, затем обновляет локальную базу
(для серии — повторно загружает календарь, включая сохранённую историю).
Чужие изменения, сделанные после открытия формы, приводят к конфликту;
кнопка «Перечитать из Google» загружает актуальную версию. Если Google сохранил
изменения, но перечитать календарь не удалось, интерфейс сообщает об этом
отдельно. Удаление из этой формы относится только к одному событию.

Тип события определяется по метке `[Спект]` / `[Спектакль]` — показ,
`[Реп]` / `[Репетиция]` — репетиция. Если такой метки нет, распознаются
отдельные слова `Спект`, `Спектакль`, `Реп`, `Репетиция` вне скобок.
Например, `Репетиция [Цианистый Калий]` — репетиция с опросом в чат спектакля,
`Спектакль [Цианистый Калий]` — показ. Поддерживаются также круглые скобки,
регистр, лишние пробелы и точка после сокращения не важны.
Название внутри скобок сохраняется при поиске спектакля и его чата.
Название определяется отдельно: сокращение `ЛГ`
сопоставляется с «Любовь Громова»; оно должно быть отдельным словом.
`ЛГ[Спект]` попадает в показы, `ЛГ[Реп]` — в репетиции «Любовь Громова».
В карточке сохраняется исходный заголовок и показывается расшифровка сокращения.
Без указания типа известное название (например, `МИКРОПОЛЬ`) означает показ.
Сервер использует каталог «Спектакли и чаты» и сохранённые варианты названий.
Внешний показ без чата можно назвать `Фрекен Жюли [Спект]`: метка определяет
тип без добавления в каталог. Также можно добавить спектакль в «Спектакли и
чаты» с пустым ID чата; тогда его название без метки распознаётся как показ.
Основные фильтры: «Все», «Репетиции», «Спектакли», «Прочее» — только если
есть текущие или будущие события в загруженном диапазоне 60 дней. Названия
внутри выбранного типа доступны в выпадающем списке с количеством событий;
«Прочее» включает и повторяющиеся группы. По умолчанию открыты репетиции,
а если их нет — «Все». Исчезнувший фильтр сбрасывается, история сетки сохраняется.
Цвет репетиции определяется постоянным ID спектакля: переименование,
сокращение и набор видимых дат его не меняют. Все показы имеют общий зелёный
цвет. ID спектакля и ID повторяющейся группы принадлежат разным таблицам:
для цвета используются индексы `2 × ID − 1` и `2 × ID` соответственно,
поэтому одинаковый числовой ID этих сущностей не задаёт один и тот же
цвет. Остальные события получают цвет группы, если встречаются
минимум в три разные даты за период от 90 дней назад до 60 дней вперёд.
Названия нормализуются без учёта регистра, пунктуации, пробелов и ё/е;
близкие варианты объединяются при сходстве не ниже 90% и не более двух
правок Левенштейна. Короткие названия, номера и имена ведущих МК/интенсивов
защищены от приблизительного объединения. Новый вариант должен совпасть
со всеми названиями ровно одной группы; цепочки сходства не объединяются.
ID и названия групп сохраняются в БД, поэтому цвета не зависят от выбранных
дат и перезапуска. Для лабы действует общее правило повторяемости.
Разовые и редкие события, а также аренда и уборка остаются серыми в «Прочем».
Группировка не определяет тип события, спектакль или чат и не даёт право
на отправку опроса.
Насыщенность цветных групп одинакова; прошедшие события в сетке по-прежнему
приглушены. Карточки явно подписывают тип, а выбранная кнопка фильтра имеет
тёмный фон. Цвета сетки и карточек совпадают. Фильтры управляют списком;
недельная сетка показывает все события.

Слова о группе не определяют тип, цвет, фильтр или доступность опроса.
Ручные и автоматические опросы доступны только для репетиций; название
спектакля или сохранённый ручной выбор определяет чат. При неизвестном
спектакле администратор выбирает его перед ручной отправкой. Месячный
список дат включает репетиции независимо от группы и наличия спектакля.
Ассистент использует эти же правила. Старое поле группового фильтра не
используется и не создаётся в новой БД; существующие данные не удаляются.
Репетиция не записывается в график как назначенный спектакль.

Финансовая синхронизация сохраняет ID неизменившихся записей. При удалении
проверяется версия записи (`expected_fingerprint`) и полное совпадение строки
в Google Sheets. Неоднозначные одинаковые строки удаляются вручную в таблице.
Если Google не подтвердил удаление, локальная запись сохраняется.

Процесс запускайте **в одном экземпляре / с одним worker**: бот, планировщик
и блокировка финансовой синхронизации работают в этом процессе. Google-вызовы
выполняются вне asyncio-цикла. При остановке фоновые задачи отменяются и сессия
бота закрывается. Автоперезагрузка по умолчанию выключена; для разработки —
`API_RELOAD=true`.

## Модерация комментариев канала

Бот проверяет новые и отредактированные текстовые сообщения в привязанной группе
обсуждений одного канала. Текст или подпись к медиа и скрытые ссылки отправляются
той же модели через `get_llm_client()`, что использует ассистент (`LLM_PROVIDER`
и настройки выбранного провайдера). Имена и ID авторов остаются в локальном аудите,
не влияют на классификацию. Модель не получает инструменты ассистента.

Есть три результата: `spam`, `allow`, `review`. Уверенный спам по умолчанию
**удаляется автоматически**, обычный комментарий остаётся. При сомнении модели,
ошибке API, отключённой LLM или неверном формате ответа модератор получает
одну карточку с кнопками «Спам — удалить все» / «Не спам — оставить все».
Повторы добавляются в эту же карточку; счётчик обновляется без нового уведомления.
Подтверждение применяется ко всем неизменённым сообщениям группы, с повторной
проверкой прав и статуса каждого автора. Автор не блокируется.
`MODERATION_AUTO_DELETE=false` отправляет на такое подтверждение также уверенный спам.

Кеш и группы проверки хранятся в SQLite (`moderation_decisions`,
`moderation_review_items`) и переживают перезапуск. Срок — **24 часа** с решения,
попадания в кеш его не продлевают. Решение человека сохраняется на новые 24 часа.
Совпадают тексты после нормализации Unicode, регистра, пробелов и невидимых
символов, независимо от автора, в пределах одной группы обсуждений и получателя
уведомлений. Пунктуация, слова и адреса скрытых ссылок сохраняются: перефразирование,
цитирование или добавление отрицания требуют новой оценки. Решения модели «не спам»
не кешируются; решение человека «не спам» кешируется. Кеш не обходит
исключение для администраторов, проверки редакций и результат предыдущего удаления.

Политика модели: сторонняя реклама, лёгкий заработок, мошеннические предложения,
казино и объявления о наборе работников (включая театральные вакансии) — спам.
Ссылка или контакты для этого не обязательны. Критика, мат, вопросы и жалобы
с цитатой спама сами по себе не повод для удаления. Решение модели вероятностное;
неопределённые случаи должны идти на ручную проверку. Локального regex-fallback нет.

Настройка на сервере в `.env`:

```dotenv
MODERATION_CHANNEL=@your_channel
MODERATION_AUTO_DELETE=true
LLM_ENABLED=true
# Необязательно: по умолчанию уведомления получает ADMIN_ID.
MODERATION_ADMIN_ID=123456789
```

Пустой `MODERATION_CHANNEL` выключает модерацию. Вместо @username можно указать
числовой ID канала вида `-100…`. Настоящий канал и ID получателя не коммитьте.

В логах `Moderation received`
и `Moderation verdict` содержат ID сообщения и результат без текста и имени автора.

1. Добавьте бота администратором **в привязанную группу обсуждений**, с правом
   удаления сообщений. Одних прав администратора канала недостаточно.
2. Получатель уведомлений должен открыть личку бота и нажать `/start`.
3. После обновления кода и `.env` выполните `./bot restart`; фронт пересобирать
   не нужно. В личке отправьте `/moderation`: бот проверит привязку и свои права.
4. Для оценки старого комментария перешлите его боту в личку от получателя
   уведомлений. Модель проверит текст и ссылки. Обычная пересылка
   пользователя не содержит ID исходной группы и сообщения: подтвердить источник
   и удалить оригинал по ней нельзя. Карточка будет без кнопки удаления.
   Посты каналов и пересылки без текста не проверяются.

Telegram разрешает боту удалять сообщения только моложе **48 часов**;
для более старого комментария проверка возможна, удаление — вручную через
Telegram ([ограничения deleteMessage](https://core.telegram.org/bots/api#deletemessage)).
Посты, автоматически пересланные из канала, сообщения администраторов обсуждения
и самого бота пропускаются. Проверяются все текстовые сообщения обсуждения,
а не только ответы под последним постом. Фото и видео без подписи, аватары
и описание профиля не анализируются.

История старых сообщений автоматически не загружается: перешлите комментарий
боту в личку.
При ошибке проверки комментарий остаётся и попадает на групповую валидацию.
При потере ответа Telegram на отправку карточки она автоматически не дублируется:
бот пытается отправить отдельное предупреждение без кнопок; проверяйте комментарии вручную.
Удаление выполняется до отправки отчёта;
сбой доставки отчёта не отменяет удаление и не сбрасывает его результат в БД.
Ошибки пишутся в `./bot logs`. Решения и версии комментариев сохраняются в SQLite, поэтому
повторное нажатие и старая кнопка после обработанного редактирования не удаляют
сообщение повторно. При неизвестном результате удаления повтор блокируется:
проверьте комментарий в Telegram. Сохраняйте БД между перезапусками и запускайте
один экземпляр бота. Обсуждение канала должно отличаться от рабочего `GROUP_CHAT_ID`;
его участники не получают доступ к Mini App через эту настройку.

## Обновление и проверки

При обновлении защиты доступа нужно развернуть **и backend, и frontend**:
старый frontend не передаёт подпись Telegram и получит 401.
Перед обновлением сохраните резервную копию SQLite обычным способом.

Из корня репозитория, с активированным виртуальным окружением сервера:

```bash
git pull
python -m pip install -r backend/requirements.txt
./bot restart --build
```

Для `./bot restart` нужно один раз выполнить `./bot setup`, как описано выше.
Сохраните прежний `REACT_APP_API_URL` при сборке. После обновления заново откройте
Mini App через Telegram.
Дополнительных обязательных переменных окружения нет.

Локальные проверки используют синтетические ответы API и отдельные SQLite-БД,
не обращаются к рабочим таблицам и не отправляют сообщения в Telegram:

```bash
python -m pip install -r backend/requirements-dev.txt
PYTHONPATH=backend python -m unittest discover -s backend/tests -v
CI=true npm --prefix frontend test -- --watchAll=false --runInBand
npm --prefix frontend run build
```

Проверены подпись и права, отзыв голосов, повторное подтверждение и неопределённый
результат внешней операции, страницы календаря, часовой пояс, сохранение ID,
безопасное удаление строк, частично отправленная кампания, остановка задач,
состояние вкладок, обновление графиков и передача подписи фронтендом.
После выкладки остаётся проверить реальные подключения и сценарии в Telegram.
